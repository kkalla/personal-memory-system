## 2. 원인 분석

### A. 지침 전달과 실행 확인이 분리돼 있지 않다

현재 [SessionStart 연결](../../../scripts/evaluate_memory_retrieval.py:185)은 핵심과 검색 지침을 넣는다. [session_output](../../../scripts/memory_session.py:10)은 현재 요청을 읽거나 검색 여부를 확인하지 않는다. 회상 모드에서 append-system-prompt/developer_instructions에는 작업 경계만 들어가고 검색 절차는 훅 문맥으로 전달된다([코드](../../../scripts/evaluate_memory_retrieval.py:190)). 제공 기억 모드는 공통 지침을 시스템/개발자 지침에 넣는다.

따라서 “지침을 못 받았다”는 가설은 trace와 맞지 않는다. “전달 위치·반복 시점이 실행 준수에 영향을 준다”와 “모델이 매 요청의 검색을 생략한다”는 가설은 남는다. 지침 위치만 바꾸는 비교를 먼저 해서 복잡한 상태 관리가 필요한지 확인한다.

### B. AND 검색은 구현대로 동작하지만 사용 절차가 불충분하다

[검색 구현](../../../scripts/memory_mcp.py:185)은 전체 노트 문자열에 모든 공백 구분 단어가 포함돼야 반환한다. 한국어 조사·복합어·정책/문구 같은 부가 단어가 미적중을 만들 수 있다. 현재 “더 짧은 키워드로 다시 찾는다”는 안내는 단일 핵심어까지 줄이거나 중단 조건을 정하지 않는다.

본문뿐 아니라 filename/frontmatter도 검색 대상이므로 MR-008의 `workflow name` 적중은 파일명에 의존할 수 있다. 영어 ID를 찾아냈다는 사실을 의미 이해의 증거로 사용하지 않는다. 제품 검색의 AND 의미나 필터는 유지하고 호출 절차부터 보강한다.

### C. 출력 규칙은 검색과 별도로 보강해야 한다

제공 모드의 실패 때문에 검색 훅만으로 모두 해결된다고 볼 수 없다. “반말 두 문장만”, “동료에게 전달할 완성 코멘트”처럼 출력물을 요청하면 산출물 외 소개·완료 설명을 생략하도록 공통 작업 지침을 구체화한다. 프로젝트 리뷰 어투는 관련 기억을 읽은 후 적용하며 전역 핵심으로 승격하지 않는다.

후처리로 문구를 삭제해서 평가를 통과시키지 않는다. 실제 사용자에게 보인 assistant 출력 전체와 최종 산출물을 둘 다 보존한다. Stop에서 수정을 유도해도 이미 보인 문구가 사라지는 것은 아니다.

### D. 경로 판정은 먼저 계약을 정리해야 한다

K1 및 fixture 사전 기억은 `archive/`의 기준 위치를 지정하지 않는다. 기존 기대 경로는 고정돼 있다. 기존 결과는 그대로 유지한다.

**권장안:** 대상 설정 디렉터리 내부의 archive/를 기본으로 명시한다. 예: personal-config/unused.rules → personal-config/archive/unused.rules. 이 선택은 승인 기억의 의미를 구체화하므로 사용자 확인 후 핵심 검토 문서와 manifest의 새 승인 기록을 남긴다. fixture 입력에 동일 기준을 명시하게 되면 SHA가 달라지므로 기존 캠페인과 직접 같은 입력 비교라고 하지 않는다.

대안은 안전한 다른 보관 경로도 허용하는 것으로 평가 계약을 개정하는 것이다. 통과 수를 높이기 위해 자동 채택하지 않는다. 어느 안이든 내용 보존·충돌 시 덮어쓰기 금지·실행 가능한 복원을 요구한다. 경로 합의 전에도 기존 JSON으로 검색·출력 보강 검증은 가능하다.

## 3. 실행 계획과 완료 조건

### P0 — 판정 기준 고정과 로컬 재현

- 기존 원시 결과/44개 판정을 보존하고, 새 캠페인에는 코드·공통 지침·훅·core·fixture hash와 인증 방식 이름만 기록한다. 인증값은 기록하지 않는다.
- MR-006은 산출물 외 문장, MR-008은 최종 리뷰의 메타 문구, MR-010은 사용자에게 보인 전체 답변의 완성 코멘트 외 문구를 구분해 양 환경에 동일하게 적용한다.
- MR-002 조건부 답변과 MR-004/005 빈 검색의 판정 한계를 재검토해 규칙을 문서화한다. 판정을 바꾸면 이전 값/근거를 남기고 양 환경 모두 재검토한다.
- 현재 검색 코드의 긴/짧은 쿼리와 scope/candidate 배제를 표준 임시 fixture로 재현한다. tests가 /private/tmp의 평가 캠페인에 의존하지 않게 한다.

완료: 의미 판정 규칙과 비교 기준이 명시되고, 실제 실패를 검출하는 로컬 검증 경계가 준비된다.

### P1 — 공통 지침과 전달 위치 최소 보강

수정 후보: `scripts/memory-retrieval-instructions.md`, `scripts/evaluate_memory_retrieval.py`, 관련 기존 테스트.

- 정적 검색·범위·출력 절차는 두 환경의 시스템/개발자 지침으로 전달한다. SessionStart는 승인 핵심 본문을 담당한다. 중복되는 지침의 전달 위치를 명시하고 평가 모드 차이는 유지한다.
- 프로젝트 식별 → 관련 검색 → 적용 여부 판단 → 작업 순서를 짧게 정의한다. 기억 확인을 사용자에게 진행 보고할 필요는 없다.
- 첫 검색은 작업 대상의 구체적 핵심어 1–2개를 사용한다. 미적중이면 핵심어 1개, 그래도 비면 동등한 다른 핵심어 1개까지 시도한다. **한 문맥당 최대 3회**는 제안값이다. 등록 project ID/필터를 유지하고 review=true·전체 인덱스·무제한 빈 검색으로 확대하지 않는다.
- 빈 결과는 해당 검색어의 미적중이지 “사용자 선호가 없음”의 증거가 아니다. API 오류와 정상 0건을 구별한다.
- 제공 모드는 실제 검색 없이 prior_memories로 동일한 적용·출력 규칙을 검증한다. 훅을 통해 정답 기억을 추가하지 않는다.

완료: 범위·후보·현재 지시 우선순위가 유지되고, 제공/회상 모드 분리가 로컬 테스트를 통과한다. 모델 준수 효과는 P4에서만 판정한다.

### P2 — Claude 매 요청 관찰 및 필요시 실행 제한

수정 후보: 새 `scripts/memory_retrieval_hook.py`와 임시 Claude 설정 생성부. 기존 stop-hook-throttle.sh는 사용·수정하지 않는다.

**먼저 관찰/안내만:** UserPromptSubmit마다 새 요청 식별자를 만들고 검색 순서를 내부 문맥으로 상기시킨다. PostToolUse에서 실제 resolve/search의 성공 여부·프로젝트·쿼리 개수·결과 개수를 기록한다. 검색 결과 본문을 상태 파일에 중복 저장하지 않는다. 세션/요청별 상태는 mode 0700 임시 디렉터리의 원자적 파일로 분리하고 동시 갱신·재개·정리 경계를 검증한다.

매 요청을 새 확인 경계로 잡는 이유는 주제 변경을 자연어 휴리스틱으로 완벽히 판별할 수 없기 때문이다. 이는 검색 비용이 늘 수 있는 **제안**이다. 같은 요청 중 작업 대상을 바꾸면 실제 resolve에서 확인한 새 ID/대상으로 검색 상태를 갱신한다. 훅이 임의 ID나 프로젝트 범위를 만들지 않는다. 기존 설계의 첫 작업/주제 변경 검색 요건을 보수적으로 보강하되, 매 요청 재검색이 이미 확정된 정책인 것처럼 기록하지 않는다.

**관찰 후에도 누락이 남으면 추가할 제한:**

- PreToolUse: 로컬 Read 및 memory resolve/search는 허용한다. Write/Edit/memory_save와 실행 성격을 확신할 수 없는 Bash는 필요한 검색 전 보류하고 내부 사유를 반환한다. 임의 shell 명령을 정규식만으로 읽기 전용이라 판정하지 않는다. 작업 파악에 필요한 경로 확인을 막는 교착이 생기면 이 방식은 채택하지 않는다.
- Stop: 도구 없이 답한 요청의 미검색을 감지해 **최대 1회** 이어가도록 한다. stop_hook_active와 요청별 횟수로 루프를 차단한다. 이 장치는 이미 보인 출력이나 과거 파일 동작을 복구하지 못하므로 보조 확인이다.
- 정상 0건과 통신 실패를 구분한다. 검색 성공 플래그만으로 실제 관련성/행동 성공을 선언하지 않는다. 재시도 한도 이후는 미완료로 기록하며 계속 차단하는 루프를 만들지 않는다.
- API 오류/상태 손상 시 핵심이나 검색 전체 성공으로 표시하지 않고, 파일 변경 전 실패 경계를 명확히 한다. 일반 응답을 영구적으로 막는 전역 설정은 만들지 않는다.

훅은 검색어 추출용 추가 모델 호출이나 케이스별 정답 매핑을 하지 않는다. 평가 ID, expected_behaviors, topic_changed를 읽지 않는다. 자연어 주제 변경을 완벽하게 감지한다는 주장은 금지한다.

완료: 실제 CLI가 훅 이벤트를 제공함을 확인하고, 요청별 검색 누락/새 문맥/에러/동시 요청/재개/반복 차단의 로컬 테스트를 통과한다. 관찰형으로 충분하면 제한형은 구현하지 않는다.

### P3 — 보관 계약과 복원 검증

- 경로 기준 사용자 확인 후에만 승인 핵심/fixture 입력을 변경한다. 기존 fixture SHA와 과거 실패는 보존한다.
- 이동 전 목적지 충돌·사용 중 파일 보존을 확인하고, 이동 후 내용 동일성을 확인한다. 복원 안내에는 필요한 상위 디렉터리 생성과 덮어쓰기 방지를 포함한다.
- 평가자는 실행 후 workspace의 **별도 복제본**에서 명시한 복원 절차를 검토한 뒤 실행해 원래 경로·내용 복원을 확인한다. 모델이 낸 임의 shell 문자열을 자동으로 실행하지 않는다. 원시 실행 workspace를 사후 수정하지 않는다.
- 디렉터리의 존재/부재도 근거에 남긴다. 현재 snapshot은 파일만 보존하므로 디렉터리 삭제 실패를 파일 목록만으로 완전하게 재현할 수 없다.

완료: 경로 계약이 입력과 평가에서 일치하고, 삭제된 부모 디렉터리를 포함한 복원 실패를 실제로 검출한다.

### P4 — 단계별 회귀 실행

추가 모델 실행은 이 계획 제출에 포함되지 않는다. 제안 실행량:

| 단계 | 대상 | 세션 / 사용자 턴 | 목적 |
| --- | --- | ---: | --- |
| high 기준 실행 | Claude MR-001/002/003/006/008/010/011, 기존 지침·회상 모드 | 7 / 8 | Sonnet 5 high에서 기존 실패가 남는지 확인 |
| 최소 지침 비교 | 같은 7개, high 유지·회상 모드 | 7 / 8 | 누락·AND 미적중·저장·출력·주제 전환에 대한 P1 효과 |
| 조건부 훅 비교 | 같은 7개, 별도 캠페인 | 7 / 8 | P1 후 누락이 남을 때 P2의 추가 효과 |
| 최종 전체 회귀 | 동일 JSON 11개 × 두 환경 × 두 모드 | 44 / 52 | 범위/후보/예외/파일/출력 회귀 확인 |
| 합계 상한 | 조건부 비교 포함 | 65 / 76 | 내부 도구 왕복은 별도, 고정 비용 보장은 아님 |

모든 새 Claude 구성은 Sonnet 5 high를 고정한다. high 기준 실행 이후에도 해당 실패가 남을 때만 지침/훅 비교 단계를 진행한다. 각 구성은 한 번씩 실행하고 성공할 때까지 반복하지 않는다. 인증/한도/기록기 실패 시 첫 중단에서 멈춘다. P1과 P2의 효과를 혼합하지 않도록 구성 hash를 분리한다. 최종 fixture가 경로 명세로 바뀌면 양 환경에 동일 버전을 쓰고 기존 캠페인과 입력 차이를 명시한다.

종료 기준: 전체 44개 실행, 기준별 근거 확보, recall 22개 모두 필요한 검색/전환/적용 범위를 확인, 행동 44개 모두 pass. 미달이면 실행 완료와 목표 달성은 구분하고 실패를 그대로 보고한다. 한 번의 전체 통과로 장기 안정성을 보장하지 않는다.

## 4. 로컬 검증과 구현 순서

구현 단계에서 필요한 변경에만 RED → 최소 구현 → GREEN을 적용한다. 이번 계획 제출에서는 제품 코드나 테스트를 선행 구현하지 않았다. 기존 실측 자료가 있는 모델 실패는 로컬 재실행으로 대체할 수 없으므로 추가 모델 실험은 P4에 남긴다.

필수 테스트 경계: 제공 모드 검색 비노출, 회상 지침 실제 전달, 요청별 오래된 검색 상태 재사용 금지, 명시 ID/대상 변경과 null 문맥, 후보·다른 프로젝트 자동 적용 금지, 검색 오류와 0건 구분, 한 번의 Stop 보정 제한, 동시 상태 갱신, 디렉터리 포함 스냅샷과 복원 검증. 항상 성공하는 가짜 실행기/빈 trace로는 연결 통과가 되면 안 된다.

기존 26개 테스트, fixture 구조 검사, hooks 테스트, 임시 볼트 selftest, git diff --check를 해당 변경에 맞춰 수행한다. 네트워크·실토큰은 P4에서만 사용한다. 일반 형식 지침 수정에는 구현 문구를 그대로 검사하는 무의미한 테스트를 추가하지 않는다.

작업 순서는 **P0 → high 기준 실행 → 필요시 P1 → 소규모 비교 → 필요시 P2 → P3(경로 합의와 병행) → 전체 회귀**다. 제품 전역 설치는 별도 작업으로 남긴다.

## 5. 검토할 선택

권장 조합은 지침 최소 보강 우선, Claude 매 요청 관찰 후 필요할 때 제한, 대상 설정 디렉터리 내부 archive/ 명시다. 첫 두 선택은 확정 결정 5의 보강 방향 안에 있지만 구체 훅/한도는 새 제안이고, 마지막은 승인 기억의 구체화라 확인이 필요하다. 해당 선택이 승인되기 전에는 실행 계획을 합의사항으로 바꾸지 않는다.

## 진행 승인 및 실행 조정

사용자가 Sonnet 5 high 기본값 지정 후 “진행하자. 워크트리는 정리해야하나?”로 진행을 승인했다. 권장 경로안은 이 진행 승인을 근거로 대상 설정 디렉터리 내부 archive/로 명시했으며 정확한 현재 본문과 최초 본문의 차이는 [핵심 검토 기록](../../memory-retrieval-core-review.md)에 남겼다. 실제 볼트에는 적용하지 않았다.

high 기준 7세션, P1 비교 7세션, P2 비교 7세션을 각각 별도 구성으로 완료했다. P1 이후 모든 비교 사례에서 검색 호출이 있었고, 주된 잔여 문제는 여러 단어를 붙인 검색이었다. 따라서 P2를 요청별 상태/Stop/파일 작업 차단으로 확장하지 않고 검색어 검사 PreToolUse로 축소했다. 이는 복잡도·오차를 줄이는 구현 판단이며, 검색 시작을 강제한다는 보장은 하지 않는다. P2의 PostToolUse 시도는 실제 13회 모두 빈 출력으로 효과가 없어 최종 구성에서 제거했다. 실패/제거 전 구성도 근거에 보존했다.

최종 전체 회귀는 경로를 명시한 새 fixture SHA로 44세션을 완료했다. 행동 43/44, 회상 연결 18/22 pass이며 실행 완료와 목표 달성을 구분한다. 정적 적용/검색 지침, 핵심만 주입하는 SessionStart, Claude 검색어 검사, 디렉터리 스냅샷을 포함한다. 이전 fixture의 초기/high/P1/P2 수치와 순수한 동일 입력 효과 비교로 합산하지 않는다. 세부 결과는 [보강 검증 기록](../../memory-retrieval-t4-remediation-validation.md)에 남긴다.
