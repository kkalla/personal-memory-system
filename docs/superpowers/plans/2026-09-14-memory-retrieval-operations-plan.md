## O1 — 구체적인 적용 묶음 준비

실제 경로에 쓰기 전에 저장소 안에 적용 명세·변경 전후 패치·파일별 복구 목록을 준비한다. 이 단계에서는 기존 운영 스킬의 심볼릭 링크 대상도 편집하지 않는다.

1. CLI 버전, 실제 설정 위치·우선순위, 훅 신뢰 설정, 프로젝트/플러그인 MCP 중복을 확인한다. 설치된 CLI의 이벤트 입력을 통해 `session_id`, `prompt_id`, `tool_use_id`와 응답 형식이 검증 코드의 기대와 맞는지 확인한다. 불일치는 어댑터 설계·로컬 검증으로 해결한 뒤 적용한다.
2. 원본 파일의 hash·권한·심볼릭 링크 경로를 기록하고 비밀값이 출력되지 않는 설정 패치를 만든다. 토큰을 설정 예시나 저장소 백업에 포함하지 않는다.
3. 최초 프로젝트 등록안은 현재 작업 경로 `/Users/max/00_Projects/95_personal-memory` 한 개부터 제시한다. 새 UUID v4를 준비하되 등록 실행 전까지 미등록이라고 표시한다. fixture ID를 복사하지 않는다. 다른 checkout·워크트리는 같은 프로젝트라는 명시 근거가 있을 때만 alias로 제안한다.
4. 승인된 `scripts/memory-core-approved.json`과 출처 파일 존재·현재 충돌 여부를 검토한다. 원본 전체를 전역 확정으로 바꾸지 않고 승인 본문만 `core-manifest.json`에 설치할 예정이다. 문구 변경이 필요하면 별도 확인 대상으로 분리한다.
5. 검색할 기존 노트의 최초 전환 목록을 만든다. 각 항목에 원문, 제안된 범위·상태·프로젝트 ID·이유, 본문 유지/분리 여부를 표시한다. 소수의 명확한 항목만 선정하고 나머지 104개는 원본과 인덱스에 보존한다. 사용자 확인이나 기존 명시 근거 없이 confirmed/global로 승격하지 않는다.

핵심 설치만으로 기존 104개가 검색 가능해지는 것은 아니다. 최초 전환이 0건이면 “핵심 제공 및 검색 배선만 적용, 레거시 자동 검색 미전환”으로 명시하고 전체 운영 완료라고 하지 않는다.

## O3 — 적용 전 검증과 검토 가능한 최종안

- 임시 볼트·임시 CLI 설정으로 **운영 예정 구성**을 먼저 검증한다. 평가 전용 서버 대신 실제 `memory_mcp.py`를 사용하며, 실제 볼트 쓰기는 하지 않는다.
- 설정 병합 시 기존 Orca·보안·Stop 훅이 남는지, 같은 핵심이 두 번 들어가지 않는지, 프로젝트 미등록·주제 변경·후보 제외·핵심 손상 시 동작을 확인한다.
- 새 어댑터/병합 도구 등 실행 코드가 필요할 때만 잘못된 입력을 거부하는 RED → 최소 구현 → GREEN으로 검증한다. 기존 로컬 테스트와 훅 테스트·selftest·fixture 구조 검증을 재사용한다. 구조 통과와 모델 행동은 별도 기록한다.
- 모델 확인은 기존 기본값 Claude `claude-sonnet-5/high`, Codex `gpt-6-astra/low`를 유지한다. 운영 스모크는 환경당 핵심 제공, 관련 검색, 두 번째 요청의 문맥 변경, 임시 저장/후보 제외를 한 세션에서 4턴으로 확인한다. 최대 2세션·8턴, 같은 구성 자동 재시도 없음. 기능 동작이 바뀌는 보강이 필요하면 기존 전체 44세션·52턴 회귀를 별도 계획하고 이번 스모크 결과와 섞지 않는다.
- 설치에 사용할 파일별 최종 diff, 등록 경로와 ID, 최초 전환 노트 목록, 백업/복구 경로, 검증 결과를 한 묶음으로 제시한다. 그때 실제 볼트·전역 설정 쓰기를 포함한 적용 승인을 받는다. K1–K4 본문과 S1–S6 자체는 다시 승인받지 않는다.

## O4 — 승인 후 순차 적용과 실제 환경 확인

1. 승인된 파일만 로컬 비공개 백업에 보존한다. 원본 존재 여부·hash·권한·링크를 함께 기록한다. 실행 중인 다른 에이전트의 쓰기가 없는 짧은 적용 구간을 확보하고 현재 파일이 검토본에서 바뀌었으면 덮어쓰지 않는다.
2. 기존 API로 프로젝트 등록, 핵심 manifest 저장, 승인된 최초 노트 전환을 수행한다. 각 결과를 다시 읽어 확인하며 인덱스 부분 실패는 성공으로 보고하지 않는다. 레거시 전부를 일괄 재작성하지 않는다.
3. Claude 설정·지침부터 병합하고 **새 세션**에서 실제 핵심 수신, 프로젝트 식별, 관련 노트 반환을 읽기 위주로 확인한다. 이어 Codex에도 같은 순서로 적용한다. 실제 저장 경로의 왕복은 앞선 임시 볼트 스모크로 확인하며 운영 볼트에 테스트 노트를 만들지 않는다.
4. 실제 환경 확인은 환경당 한 새 세션·최대 2턴(현재 프로젝트 → 다른 주제), 합계 최대 2세션·4턴이다. 진단 중 비밀값·기억 전문을 저장소 추적 파일에 남기지 않는다. 핵심 수신, 실제 검색 결과, 최종 행동을 각각 기록한다.
5. 알려진 MR-002 의미 불일치를 제외하고 새 실행 오류·잘못된 범위 적용·기존 훅 파손이 나오면 두 번째 환경으로 확대하지 않는다. 실패 원인과 복구 결과를 기록한다.

## 복구와 완료 기준

복구는 먼저 새 MCP·핵심·검색 지침/훅 항목을 이번 패치 단위로 비활성화하고 기존 Claude 인덱스 제공을 복원한다. 설정 전체를 과거 파일로 덮어써 동시 사용자 변경을 지우지 않는다. 볼트도 변경한 파일에 한해 현재 hash가 적용 직후와 같을 때만 이전 상태로 복원한다. 이후 새 기억이 저장됐거나 충돌이 있으면 보존하고 차이를 검토한다. 새로 만든 파일은 백업 위치에 보관하며 무조건 삭제하지 않는다. 별도 승인된 새 Stop 훅을 운영 MCP 연결 복구 과정에서 과거 30분 버전으로 되돌리지 않는다. 훅 자체 복구가 필요하면 적용 기록의 60분 원본 보존 절차를 따른다.

완료는 두 환경의 **실제 새 세션**에서 핵심 수신·등록 프로젝트 식별·승인된 검색 대상 반환·문맥 변경을 확인하고, 기존 훅 보존과 저장 계약의 임시 왕복 검증 근거가 있는 상태다. 배포 기록에는 최초 전환 수/남은 레거시 수, 실제 연결한 경로, 검증 모델·버전·구성 hash, 검색 누락 보류 및 Codex 제어/동시 쓰기 제한을 적는다. 전역 설치 완료와 모든 기억 전환 완료는 구분한다.

## 이번 계획 작성 결과

최초 계획 작성 당시 실제 볼트·전역 CLI 설정·운영 스킬·훅·launchd 변경 없음. 이후 별도 승인으로 운영 스킬·훅만 수정했으며 실제 볼트·전역 설정·launchd는 여전히 변경하지 않았다. 패키지 설치·프로젝트 등록·노트 전환·모델 호출 없음. 다음 실행 단위는 **O1–O3의 검토 가능한 적용 묶음 준비**이며, O4는 그 결과를 바탕으로 실제 적용 승인을 받은 뒤 진행한다.
