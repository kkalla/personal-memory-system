# 여러 에이전트의 개인 메모리 자동 회상

상태: 2026-09-10 사용자 최종 확정. 구현은 아직 시작하지 않았다.

## 목표와 근거

사용자가 기억을 다시 언급하지 않아도 여러 에이전트가 관련 선호·정정·제약을 적용한다. 목록 주입 성공과 실제 행동 개선은 별도로 검증한다.

확인 당시 MEMORY.md는 101줄, 28,687자, 링크 99개였다. 줄 수는 주입 비용을 제한하기에 부적절하다. Stop hook은 저장 평가를 유도하고 SessionStart hook은 인덱스 전체를 출력한다. memory_mcp.py의 memory_get은 인덱스/이름 조회이며 ensure_index_line은 100줄 제한을 강제하지 않는다. seCall이 memory/*.md를 검색하지 않는다는 근거는 README의 2026-07-30 실측 기록이다. 설치 버전 0.7.0은 확인했지만 내부 소스 재검증은 하지 않았다.

## 확정 결정

1. 저장 시 scope(global/project)와 status(confirmed/candidate)를 구분한다. 프로젝트 기억은 project_id를 갖는다. 물리 폴더 분리는 요구사항이 아니다.
2. 명시적 선호·정정·확정 결정은 confirmed로 기록할 수 있다. 추론은 candidate로 분리하고 자동 행동 규칙으로 적용하지 않는다.
3. 적용 범위가 애매하면 현재 프로젝트로 좁게 저장하고 범위가 추정됐음을 표시한다. 프로젝트 문맥도 없으면 후보로 보관한다. 전역 확대는 사용자 명시 또는 확인 후에만 한다.
4. 전역의 확정된 기억 중 프로젝트를 가리지 않고 필요한 핵심 선호·반복 정정만 짧은 본문으로 항상 제공한다. 전역 기억 전체를 주입하는 것은 아니다. 최초 핵심 후보는 내용과 선정 이유를 사용자에게 보여주고 확정한다.
5. 나머지는 첫 작업 파악 시와 작업 대상·주제 변경 시 검색한다. 공통 에이전트 지침으로 시작하고 검색 누락이 검증되면 환경별 훅 보강을 검토한다.
6. 기존 memory MCP에 memory_search를 추가한다. 초기 범위는 키워드 검색과 프로젝트·유형 필터다. secall은 과거 대화 검색에 유지한다. 의미 검색은 회귀 테스트에서 키워드 검색의 부족함이 드러난 뒤 검토한다.
7. 전체 인덱스의 100줄 제한을 없애고 전체 목록은 보존한다. 항상 제공하는 핵심 본문에는 토큰 예산을 둔다. 구체 예산과 토큰 계산 방식은 아직 정하지 않았다.
8. 충돌 우선순위는 현재 사용자 명시 지시 → 해당 작업 명시 규칙 → 저장된 일반 선호다. 추론 후보는 참여하지 않는다. 충돌한 옛 기억은 적용을 중단하되 영구 변경과 이번 작업 예외가 불분명하면 자동 덮어쓰지 않는다.
9. JSON 회귀 케이스를 먼저 작성한다. 첫 검증 대상은 Claude Code와 Codex다. 기억이 주어진 상태의 행동 검증과 실제 환경의 회상 연결 검증을 분리한다.

## Success Criteria

- 기억을 요청하지 않은 작업에서 관련 선호·제약이 최종 행동에 반영된다.
- 무관한 프로젝트 기억, 추론 후보, 현재 지시와 충돌하는 옛 기억을 잘못 적용하지 않는다.
- 작업 주제 변경 후 필요한 기억을 다시 찾는다.
- 전역/프로젝트 적용 범위를 보존한다. 제한된 프로젝트 정정을 전역으로 일반화하지 않는다.
- 동일 JSON 케이스를 Claude Code와 Codex에 적용 가능하며, 모델·환경별 결과와 실패 원인을 구분해 남긴다.
- 검색 호출 또는 기억 문구 언급만으로 행동 성공 처리하지 않는다. 실행하지 않은 케이스는 통과가 아니다.

## 기존 구현 — 재사용

- scripts/memory_mcp.py: memory_get(name=None), memory_save(kind, slug, description, body, tags=None), ensure_index_line(slug, filename, description), write_atomic(path, text), existing_created(path).
- 기존 파일 형식, 원자적 전체 쓰기, scrub_secrets 재사용을 보존하고 필요한 메타데이터/검색 계약을 확장한다.
- skills/memory-tick/session-start-memory.sh, stop-hook-throttle.sh 및 test_hooks.sh가 있다.
- 실제 볼트는 /Users/max/99_memory/memory. 회귀 fixture는 실제 볼트를 수정하지 않는 임시 저장소를 쓴다.

## Implementation Tasks

### T1 — JSON 회귀 케이스와 평가 계약 (다음 세션)

기존 기억을 읽고 실제 사례 기반 약 10개 케이스를 JSON으로 작성한다. 상황, 사전 기억, 사용자 요청, 기대 행동, 금지 행동을 표현하고 안정적인 케이스 ID를 둔다. 명시적 전역 선호, 프로젝트 제약, 범위 추정, 무관한 프로젝트, 후보 제외, 현재 지시 충돌, 일회성 예외, 주제 변경, 표현이 다른 검색 요청, 여러 환경의 동일 행동을 포함한다.

케이스 구조와 판정 기준을 정의하고 로컬 검증기를 TDD로 만든다. 검증기는 누락 필드/중복 ID 등 계약 오류를 실제로 거부해야 한다. fixture 구조 검증과 에이전트 행동 검증 결과를 구분한다. 모델 호출 없이 수행할 수 있으며 실토큰은 불필요하다. T1에서 모델 실행 하네스나 검색 제품 코드는 만들지 않는다.

### T2 — 핵심 기억 후보 및 저장 계약

기존 노트에서 최초 핵심 후보와 이유를 제시해 사용자 확인을 받는다. scope/status/project_id/범위 추정 표기, 기존 메타데이터 없는 노트의 처리, 프로젝트 ID 규칙, 핵심 토큰 예산을 구체화한다. 이 세부사항의 구체값은 이번 대화에서 확정되지 않았으므로 임의로 이미 합의됐다고 적지 않는다.

### T3 — 저장·검색 구현

기존 MCP의 저장 계약을 확장하고 memory_search 키워드 검색·필터를 구현한다. 원본 보존, 후보 격리, 범위 제한, 기존 API 호환을 검증한다. 전체 인덱스 상한을 제거한다.

### T4 — 두 환경 연결 및 회귀 실행

확정된 핵심 본문 주입과 검색 시점 지침을 Claude Code/Codex에 연결한다. T1 JSON으로 행동 검증과 실제 회상 연결 검증을 실행하고 결과를 분리한다. 실제 모델 실행에는 설치된 CLI·인증 및 토큰이 필요하다. 실행량을 먼저 산정한다. 결과를 보고 검색 보강 필요성을 판단한다.

## 현재 작업 경계

설계만 확정됐다. 공개 함수 추가, JSON 케이스 작성, 제품 코드 변경, 모델 회귀 실행은 아직 없다. 기존 Stop hook 30→60분 변경은 이번 설계 작업 이전부터 워킹트리에 있었으며 이번 작업에 포함시키지 않는다.
