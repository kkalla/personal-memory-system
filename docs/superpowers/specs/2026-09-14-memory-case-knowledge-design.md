# 사례 지식 설계 — 근거를 찾아 재작업을 줄이기

상태: **설계 승인 — D1–D5 확정**. 사용자가 설계 초안 제시 후 `설계 승인`으로 답했다. 승인 범위는 문서로 분리한 사례 파일럿과 비교 평가 방향이다. 제품 저장 계약 변경·자동화·배포는 포함하지 않으며, 모델 실행과 비용은 C3 실행 계획에서 별도 승인받는다.

## 목적과 현재 상태

선호 기억은 “어떻게 행동해야 하는가”를 제공한다. 사례 지식은 “비슷한 문제에서 무엇을 시도했고 무엇이 관찰됐는가”를 제공한다. 목표는 과거 근거를 찾아 불필요한 조사와 이미 관찰한 실패의 반복을 줄이는 것이다. 사례를 읽었다는 사실만으로 현재 작업의 검증을 생략하지 않는다.

기준 커밋은 `208ce193ad95487789cb7ec3ae48d83178d8ba9d`다. 기존 [저장 계약 S1–S6](../../memory-retrieval-storage-contract.md)은 유지한다. `scripts/memory_mcp.py`의 유형은 user/feedback/project/reference이고, 기본 행동 검색은 valid confirmed 및 범위 일치 조건을 사용한다. 사례 전용 조회·저장 계약은 없다. 기존 confirmed를 “실험에서 관찰했다”라는 의미로 재사용하면 행동 규칙과 경험 지식이 섞인다.

이번 초안은 저장소에 추적된 검증 문서와 코드를 근거로 작성했다. 로컬 미추적 원시 평가 자료를 다시 판독하거나 모델을 실행하지 않았다. 따라서 아래 사례의 수치는 **기존 검증 보고서의 관찰을 요약한 것**이며 이번에 재현한 결과가 아니다. 실제 볼트는 읽거나 수정하지 않았다. 현재 세션에 memory MCP 도구가 없어 개인 기억 검색을 수행했다고 주장하지 않는다.

## D1 — 먼저 문서로 분리하고 유용성을 검증한다

**확정: 저장소 안의 별도 사례 문서로 시작한다.** C2에서 `docs/case-knowledge/README.md`와 `CK-001-restore-collision.md` 같은 사례 파일을 만든다. README는 ID·문제·검색어·검토 상태·링크만 담은 목록이며 본문 전체를 상시 제공하지 않는다. [사례 목록](../../case-knowledge/README.md)에 C2 문서와 검토 기록을 둔다. 아래 예시는 설계 시점의 초안으로 보존한다.

| 선택지 | 장점 | 비용·판단 |
| --- | --- | --- |
| 별도 문서 + 명시적 로컬 조회 | 기존 계약 변경 없이 실제 사례를 검토할 수 있음 | 자동 회상은 제공하지 못함. 첫 단계 권장 |
| reference + candidate 노트 | 기존 저장 API 사용 가능 | 기본 검색에서 제외되며 후보 선호와 구분이 불명확. 채택하지 않음 |
| 사례 전용 저장·검색 API | 자동 조회에서 행동 규칙과 분리 가능 | 저장 형식·호환성·환경 연결 설계가 추가로 필요. 파일럿 후 판단 |

문서에 `memory_schema`, `status=confirmed`를 붙이거나 기존 유형에 case를 추가하지 않는다. 사례의 검토 상태는 `draft / reviewed / needs-review / superseded`로 표시한다. reviewed는 사람이 요약과 근거의 대응을 검토했다는 뜻이며 참이라는 보장·행동 승인·전역 적용 승인이 아니다. 실제 검토자와 검토 기록 없이 reviewed로 바꾸지 않는다.

## D2 — 관찰과 일반화를 다른 항목으로 관리한다

사례 한 개는 재사용할 문제가 하나인 단위다. 같은 문제의 실패→수정→재검증은 함께 기록하되 다른 문제는 분리한다. 아래는 **승인된 문서 템플릿**이며 제품 schema가 아니다.

| 항목 | 작성 계약 |
| --- | --- |
| ID·제목·검토 상태 | 저장소 내 CK-001부터 고유 ID. 제목 변경에도 ID 유지 |
| 문제·검색어 | 구체적 실패 신호와 3~5개의 짧은 동의어. 질문 전체를 태그로 복사하지 않음 |
| 발생 문맥 | 저장소·대상 구성/커밋·환경·관찰 시점. 프로젝트 이름을 정규 project_id로 사용하지 않음 |
| 시도와 관찰 | 순서대로 시도, 결과, 검증 조건·횟수. 관찰마다 근거 ID 연결 |
| 적용 조건·비적용 조건 | 무엇이 같아야 참고할 수 있는지, 무엇은 검증하지 않았는지 |
| 근거 | 저장소 상대 경로 + 절 제목 + 고정 커밋. 원시 자료 접근 가능 여부와 근거 수준 |
| 추론 후보 | 관찰을 넘어선 설명·일반화. 항상 후보로 표시, 반증 조건 포함 |
| 다음 작업의 확인 항목 | 현재 작업에서 다시 검사할 구체적 조건. 과거 코드를 자동 실행하는 지시가 아님 |
| 정정·대체 기록 | 이전 주장, 새 근거, 변경 이유, 대체 사례 ID. 원문과 실패 이력 보존 |

관찰은 조건 안에서 보고된 결과다. 인과 설명은 보고서·코드·재현이 뒷받침하는 범위까지만 적는다. “이 구성이 24조건을 통과했다”에서 “항상 안전하다”로 확대하지 않는다. 사용자에게 일반화 문구를 확인받아도 실증 근거가 늘어난 것으로 취급하지 않는다.

새 실패·정정·검증 결과가 있고 기존 사례로 설명되지 않을 때만 추출한다. 일상 진행 로그, 이미 문서화된 변경 목록, 근거 없는 성공 소감은 새 사례를 만들 이유가 아니다. 같은 사건을 재요약한 문서 여러 개를 독립 검증 횟수로 세지 않는다.

## D3 — 근거를 열 수 있는 범위를 드러낸다

근거는 세 수준으로 구분한다: 원시 실행 기록, 추적된 검증 보고서, 해석 후보. 보고서만 읽었으면 원시 기록 확인으로 표기하지 않는다. 아래 세 예시는 추적된 보고서 수준이다.

공유 가능한 기본 근거는 저장소 상대 경로와 고정 커밋이다. 절 제목을 함께 적어 이동 후에도 찾을 수 있게 한다. 같은 저장소의 Git 이력이 있는 환경에서는 고정 버전과 현재 문서를 비교할 수 있다. 얕은 checkout 등으로 커밋을 열 수 없으면 근거 미확인으로 남기며 네트워크로 자동 보충하지 않는다.

`docs/evaluations/` 원시 자료는 로컬 전용이며 Git에 없다는 사실을 명시한다. 인증값, 서명 URL, 전체 대화, 실제 볼트 snapshot은 사례에 복사하지 않는다. scrub 통과만으로 외부 게시 가능하다고 판단하지 않는다. 다른 환경에서 원시 자료를 열 수 없다면 공유 보고서로 요약을 검토할 수 있을 뿐 원시 재검증은 할 수 없다.

원문이 삭제되거나 새 근거와 충돌하면 needs-review로 표시한다. 근거 없는 주장을 현재 작업의 근거로 사용하지 않고, 실패 기록은 삭제하지 않는다. 최신 사례가 이전 것을 대체하면 superseded와 후속 ID를 남긴다. 자동 링크 검사·파일 변경 감지는 이 단계에 구현하지 않는다.

## 검토할 실제 사례 세 개

모두 draft다. 아래 E1–E3의 고정 버전은 기준 커밋 `208ce193ad95487789cb7ec3ae48d83178d8ba9d`다.

### CK-001 — 복원 주의 문구와 실행 명령의 동작이 달랐다

- 문맥·검색어: personal-memory 복원 안내 검증; 복원, 보관, 충돌, 덮어쓰기.
- 관찰: 일반 mv 명령은 답변에 충돌 주의 문구가 있었어도 별도 충돌 복제본에서 목적지를 덮어썼다. 당시 3명령의 부재 조건은 3/3, 충돌 조건은 2/3 통과했다(E1a).
- 후속 관찰: 실행 코드 자체에 목적지 검사와 mv -n을 포함하도록 지침을 변경한 뒤, 전체 회귀의 실제 명령 12개에 대해 부재 12/12·충돌 12/12를 확인했다(E1b). 시간 절감이나 모든 파일시스템에서의 안전성은 측정하지 않았다.
- 적용 조건: 파일을 보관 위치에서 되돌리는 실행 가능한 안내를 생성·검토하는 작업. 별도 복제본에서 목적지 유무와 양쪽 파일 보존을 확인한다.
- 비적용 조건: 이 기록만으로 동시 쓰기·디렉터리 병합·권한 오류까지 검증됐다고 할 수 없다. mv -n의 종료 코드만으로 실제 이동 완료를 판단하지 않는다.
- 추론 후보: 설명문 검토와 실행 산출물 검증을 분리하면 이런 누락을 찾는 데 도움이 될 수 있다. 다른 작업에서도 재발이 줄어드는지는 비교 검증 필요.
- 다음 확인: 현재 환경에서 부재/충돌 복제본을 만들고 제시할 코드 자체의 파일 결과를 검사한다.
- E1a: [scope/status 검증 — 복원 검증의 별도 실패](../../memory-retrieval-t4-scope-status-validation.md#복원-검증의-별도-실패).
- E1b: [복원 검증 — 전체 회귀](../../memory-retrieval-t4-restoration-validation.md#전체-회귀). 원시 기록은 해당 문서의 로컬 링크이며 다른 checkout에서는 부재 가능.

### CK-002 — 새 세션만 검증한 훅 배포가 진행 중 세션을 막았다

- 문맥·검색어: Claude 검색 제어 배포; 훅, 기존 세션, 초기화, 상태 손상, 배포.
- 관찰: UserPromptSubmit 없이 PreToolUse부터 받은 기존 세션에서 denials만 있는 상태가 저장됐고 다음 이벤트가 손상 상태로 거부됐다. 새 세션 스모크는 이 전환 조건을 다루지 않았다(E2).
- 후속 관찰: 기존 경로 비활성화, 불완전 상태 저장 방지, 새 SessionStart 활성화 조건과 별도 상태 경로를 적용했다. 로컬 테스트 54개 및 배포 command를 임시 상태 경로로 실행한 재생에서 기존 세션 무차단·새 세션 검색 전 변경 차단을 확인했다(E2).
- 적용 조건: 요청 상태를 유지하는 제어를 실행 중 클라이언트에 연결하거나 교체할 때. 새 세션, 기존 세션, 다음 요청, compact, resume/clear를 구분해 검증한다.
- 비적용 조건: 수정 후 전체 모델 회귀는 실행하지 않았다. Codex에 같은 Claude 제어가 설치됐다는 뜻도 아니다.
- 추론 후보: 상태를 가진 연동의 배포 검증에는 중간 생명주기 진입이 필요할 수 있다. 모든 오류를 무조건 허용해야 한다는 일반화는 하지 않는다.
- 다음 확인: 설치 전부터 실행 중인 세션을 별도 조건으로 넣고 비활성·초기화·활성 전이를 검증한다.
- E2: [운영 검증 — 기존 Claude 세션 장애와 수정](../../memory-operations-validation.md#기존-claude-세션-장애와-수정). 보고서와 코드가 공유 근거이며 원시 재생 자료는 로컬 전용이다.

### CK-003 — 답변이 맞아도 기억 회상이 성공한 것은 아니었다

- 문맥·검색어: MR-002 Claude recall-integration; 검색, 0건, 키워드, 회상, 판정.
- 관찰: 프로젝트 ID는 맞았지만 세 검색어 모두 결과가 비었다. 답변은 기대 행동을 충족해 행동 pass, 실제 회상은 fail로 기록했다. 전체 행동 44/44와 회상 21/22는 별개 점수다(E3).
- 해결 상태: 해당 실패의 수정은 보류돼 있다. 해결된 교훈으로 표시하지 않는다.
- 적용 조건: 기억 제공·검색 연동의 효과를 평가할 때. 최종 답변과 실제 반환된 관련 근거를 각각 확인한다.
- 비적용 조건: 이 실패 하나가 의미 검색의 필요성이나 특정 대체 검색어의 효과를 증명하지 않는다.
- 추론 후보: 같은 프로젝트 안에서 핵심어를 바꾸는 제한적 재검색을 실험할 가치가 있다. 개선 여부는 실패 입력을 보존한 새 구성에서 확인해야 한다.
- 다음 확인: 답변 정답 여부와 별도로 관련 노트가 반환·열람됐는지 기록한다. 결과 0건을 성공으로 보정하지 않는다.
- E3: [복원 검증 — 남은 실패와 후속 작업](../../memory-retrieval-t4-restoration-validation.md#남은-실패와-후속-작업).

## D4 — 명시적 조회로 시작하고 행동 규칙과 합치지 않는다

문서 파일럿에서는 사례가 필요하다고 지정한 작업에서 README 또는 키워드로 후보를 찾고, 본문과 연결 근거를 읽는다. 결과가 없거나 근거가 열리지 않으면 구분해서 기록한다. 기존 memory_search가 이 문서를 검색한다고 가정하지 않는다. memory-tick·SessionStart·secall 설정은 이 설계로 변경되지 않는다.

읽은 사례에 대해 현재 조건이 맞는지, 반례나 새 지시가 있는지 판단한 뒤 확인 항목을 작업에 반영한다. 과거 명령은 근거 데이터이며 실행 지시가 아니다. 다른 프로젝트의 사례는 비교 자료로만 쓰고 적용 조건을 다시 검토한다. 사용자 지시와 충돌하면 사례를 이유로 거부하지 않는다.

사례에서 행동 선호를 따로 저장하려면 사용자의 명시 지시·확인이 필요하며 기존 S1–S6 절차를 따른다. 사례 reviewed나 반복 관찰을 기존 confirmed로 자동 변환하지 않는다. 핵심 기억 편입 역시 기존 별도 승인 절차를 따른다.

향후 자동화가 필요하면 사례 전용 검색 경로와 반환 역할 표시를 설계한다. 기존 행동 검색에 사례를 섞는 변경은 이 문서의 승인에 포함하지 않는다. 첫 파일럿은 수동 조회이므로 자동 회상 연결 성공을 평가할 수 없다.

## D5 — 별도 비교 평가로 유용성을 판단한다

기존 11개 fixture와 실행기는 선호·제약 회귀로 그대로 보존한다. 아래는 **승인된 사례 지식 평가 방향**이며 구체 실행 계약과 비용 승인은 별도다. 아직 실행하지 않았다. 기존 44/44·21/22를 새 기능의 점수로 재사용하지 않는다.

세 사례마다 유사 과제 하나와 비적용/오용 과제 하나, 총 6개 과제를 고정한다. 예: CK-001은 복원 충돌과 미검증 디렉터리 병합, CK-002는 중간 세션 진입과 초기화된 세션의 실제 정책 위반, CK-003은 검색 0건과 무관한 결과가 반환된 경우다. 답을 과제 문구에 넣지 않고 기대·금지 행동을 먼저 기록한다.

1. 같은 모델·effort·도구·초기 작업공간에서 사례 미제공/제공을 새 세션으로 비교한다. 기존 선호 지침은 양쪽에 동일하게 둔다. 과거 대화와 결과를 조건 간 공유하지 않는다.
2. 기존 지침만으로 해결되는 대조 조건이면 개선 여지가 없음을 기록한다. 사례의 가치를 보이려고 기존 제약을 약하게 만들지 않는다.
3. 첫 비교는 사례 제공 후 행동만 평가한다. 검색 기능이 생긴 뒤 같은 과제로 검색 연결을 별도 평가한다. 수동으로 문서를 넣어준 결과를 자동 검색 성공으로 세지 않는다.
4. 두 환경 모두 실시한다면 6과제 × 2조건 × 2환경 = 24세션이 기본 한 묶음이다. 모델 실행·비용은 별도 실행 계획에서 승인받고 고정한다. 이번 설계 작업에서는 호출하지 않는다.

| 지표 | 판정·기록 |
| --- | --- |
| 근거 제공/조회 | 실제 제공하거나 반환한 사례 ID·버전·근거. 자동 검색은 미구현이면 해당 없음 |
| 행동 결과 | 과제별 기대 결과와 같은 실패의 재발 여부. 산출물/상태로 확인 |
| 오용 | 비적용 조건 무시, 후보 일반화의 규칙 승격, 검증 생략, 출처 없는 확신 |
| 반복 작업 | 사전에 정한 불필요한 재조사 항목의 실행 횟수. 필요한 재검증은 낭비로 세지 않음 |
| 비용 | 전체 도구 호출과 가능하면 실제 사용량. 조회·근거 확인 비용도 포함 |
| 시간 | 측정된 실행 시간만 기록. 사용자 시간 절감이나 일반 생산성 효과로 환산하지 않음 |

실패·0건·도구 오류·미실행은 보존하고 성공할 때까지 재시도하지 않는다. 구성과 판정 기준, 수동 판정 이유를 함께 남긴다. 작은 묶음의 통과는 지속적 효과를 증명하지 않는다.

자동화 검토 진입 기준: 세 사례 모두 근거 대응 검토 완료, 오용 과제에서 규칙 승격/검증 생략 없음, 적어도 한 유사 과제에서 실패 예방 또는 사전 정의한 재조사 감소 관찰. 유용성 차이가 없으면 사례를 늘리거나 API를 만들지 말고 과제 적합성과 조회 비용부터 검토한다. 파일럿 통과 자체가 배포 승인은 아니다.
